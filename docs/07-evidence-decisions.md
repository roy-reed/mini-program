## 2. 本方案采用的默认值

| 决策 | 默认选择 | 原因／改变的影响 |
| --- | --- | --- |
| 首发载体 | 微信原生小程序 | 与流程图和微信传播一致；H5 另算身份和适配工作 |
| 抽取次数 | 每用户每活动一次 | 原图已有作品直接展示；开放重抽会改变模型与成本 |
| 用户输入 | 喜欢的称呼，1–16 字素簇 | 不依赖实名／手机号；以字体显示范围为约束 |
| 个性化方式 | 视频画面写名字，音乐不念名字 | 用户没有要求语音合成或歌手声音克隆 |
| 视频输出 | 15–30 秒竖版 MP4，20 秒估算 | 对应副歌片段宣传；最终由实际曲目确认 |
| 改名规则 | 原款式不变，用户主动更新旧函 | 兼顾流程图和不可变抽取结果 |
| 传播范围 | 明确开启分享后，持链接可看；可关闭 | 让用户知道称呼会被分享；原始作品默认非公开 |
| 内容池 | 审核过的组合，按权重随机 | 避免不协调混搭和无法导出的素材 |
| 运行路线 | 独立 API／Worker＋PostgreSQL＋COS | 保证真正合成视频，并控制异步任务一致性 |
| 规模／进度 | 100 在线压测基线，研发 4–5 周 | 全是规划假设，需要实测与团队确认 |

## 5. 仍需项目方提供的五组输入

1. 品牌与发行：乐队／专辑／曲目名称、发行日、主视觉风格与活动时间。
2. 内容与权利：副歌、背景、封面、标识和字体，以及小程序展示、视频合成、保存／分享的允许范围和期限。
3. 玩法：一次抽取是否采用、是否有特殊款、权重、称呼长度与保留策略是否调整。
4. 运营容量：总参与量、首发峰值、允许排队、可接受成本、运营和支持人员。
5. 平台条件：小程序主体／AppID、云账号与域名、收听落地入口和希望上线的窗口。

## 6. 主要风险及处置

| 风险 | 早期验证／处理 |
| --- | --- |
| 预览好看但无法导出真实音乐视频 | M0 先做姓名烧录成片并真机保存，之后再铺开动画 |
| 首发流量使渲染队列过长 | 实测单条成本与峰值，扩容 Worker／限新生成／展示等待 |
| 文字超长、字体缺字或对比不足 | 共用字体与排版策略，发布前测长名，输入时反馈 |
| 账号、类目、备案或审核条件不匹配 | 主体管理员提前在微信后台核实，与研发并行准备 |
| 内容被撤回但旧分享仍可访问 | 短期签名、版本撤回、清理存储／CDN；告知无法回收已保存副本 |
| 修改称呼或重试意外变成重抽 | 固定 invitation 款式、版本化文案、事务与并发验收 |

本仓库的本次变更只交付方案、原始流程图和占位配置，不含生产凭据、真实音频、部署、付费开通或已通过审核的保证。
