# DeepSeek / Grok 精确操作手册

版本 v1.2。目标是让每次模型调用完成一个有边界、可复核的工作单元。这里没有调用或验证用户指定的模型；名称是项目分工标签。请在你实际使用的平台选择可用的对应模型，记录显示名称/日期；不根据名称猜测上下文、价格或能力。

## 1. 固定分工

| 代号 | 执行者 | 负责内容 |
| --- | --- | --- |
| D | DeepSeek V4.1 Flash 或同级 | 工程骨架、明确的 DTO/页面/CRUD、测试夹具、文档记录 |
| G | Grok 4.7 或同级 | 事务/租约、媒体管线、身份权限、部署恢复和并发故障；审查 D 的输出 |
| C | 本对话的 Codex | 已在本方案作出架构与步骤裁决；G0–G5 门槛审查和跨模块争议裁决 |
| H | 项目负责人/管理员/测试者 | 账号、素材确认、扫码、后台操作、真机与最终上线决定 |

每张步骤卡已经指定执行者与另一模型复核者，不让实现模型重新选架构。复核者先只读 diff 和证据；发现问题给精确修改项，由原执行者修。G 写的高风险模块即使 D 复核通过，也要在对应 C 门槛通过。若 D/G 无终端或仓库能力，使用下文“纯聊天模式”，不能假装运行过命令。

## 2. 现在第一步怎么做

1. 使用 `roy-reed/mini-program` 的本次方案 PR 分支，先确认最新 SHA 与是否合并；已有工作不要覆盖。读 AGENTS、AI_START_HERE、IMPLEMENTATION_STATUS。
2. H 先按 [人工步骤 H01](18-human-operations.md) 建立账号/主体台账；同时把 S00 交给 D，记录缺项。无需先购买所有资源才能做本地工程。
3. 在仓库根目录运行 `node scripts/prepare-task.mjs S00 --role implement`；把输出作为该模型本轮输入。该命令现在已存在，只生成上下文，不执行应用开发。
4. S00 返回后，用同一编号加 `--role review` 生成复核提示，附实际 diff、命令结果和证据，交给卡片指定复核者。模型的“已完成”不是验收。
5. 按索引的默认顺序继续 S01；S04 完成后提交 G1 证据给 C，才把微信媒体链路标为通过。AppID 阻塞时可继续不依赖 H 的纯后端任务，未过门槛不能提审。

用户可把生成的输出重定向到本地 `.task-context.md`，复制到对应模型；该文件不提交。不要一次上传原来的 43 万字节合并文档。

## 3. 一张卡从开始到完成

| 顺序 | 谁 | 精确操作 | 进入下一步条件 |
| --- | --- | --- | --- |
| 1 | H/执行模型 | 记录基线提交；`git status --short` 检查现有修改；创建 `impl/Sxx-短主题` 工作分支。若有他人未提交修改，先保留隔离，不 reset/clean | 基线明确且不覆盖他人工作 |
| 2 | 执行模型 | 读卡片、规则和指定章节，核对 dependencies 与本轮 file allowlist；列出至多 5 项实现步骤 | 没有未满足的硬依赖；外部缺项被记录 |
| 3 | 执行模型 | 只实现本卡；测试直接覆盖验收行为和失败路径；不顺手重构、不修改测试让失败消失 | 指定文件和验收代码存在 |
| 4 | 有终端的一方 | 在卡片指定目录执行实际命令；保存退出码、测试数、失败信息、git SHA。不存在的脚本先按所属卡实现，不能编造通过 | 真实命令成功，手工项仍单列 |
| 5 | 另一模型 + H | 只读审查 diff、契约和证据；检查未授权文件与泄密；问题回原模型修；通过后提交并更新状态 | 自动检查＋指定复核＋需要的人工证据均齐全才 DONE |

固定证据文件 `docs/evidence/Sxx.md`：基线 SHA、实现 SHA、模型显示名称、文件清单、命令/退出码/摘要、人工证据引用、复核结论、剩余阻塞。秘密配置、原始身份、令牌、私人截图只存项目方受控位置，仓库只存去敏摘要。模板见 [任务回执](templates/task-receipt.md)。

## 4. 纯聊天模型的交付协议

如果模型不能读取仓库或执行命令，H 上传任务包与允许修改文件的当前版本；要求模型返回 **unified diff**，新文件给完整内容，禁止用“其余不变”省略关键实现。H/本地编码代理先 `git apply --check change.patch`，成功后应用；失败返回冲突位置，不让模型凭空猜本地文件。

有终端的一方执行卡片命令，把实际输出返回复核模型。纯聊天模型的状态最多是 `IMPLEMENTED_UNVERIFIED` 的回执描述，状态表保持 DOING；没有执行证据不能填 DONE。如果缺实际模型服务，保持卡片等待，不自动换到一个未说明的模型。S00只要求把未知输入和责任人列清；H流程在相应卡验收前取得必要证据，不要求所有H步骤先完成。

## 5. 修复与升级规则

第一次失败：原模型按失败测试与原始错误修复，不扩大任务范围。第二次同因失败：交给 G 定位根因，把当前卡拆成“数据/逻辑/测试”小段，父卡仍 DOING。第三次同因失败，或涉及规则/契约变更：提交 C 裁决，提供最小复现、失败命令、diff 和两个可选修复；不继续随机试错。

这不是每步都向用户请求确认：允许在卡片内修实现和测试、补必要小文件。新增生产开支、账号实名、外部发布等按已有授权与实际权限执行。产品规则/HTTP/库结构的改变必须先同步方案、契约、测试；实现模型不能悄悄切换为附件的另一套架构。

## 6. 六个检查门槛

| 门槛 | 提交给 C 的证据 | 未通过时如何继续 |
| --- | --- | --- |
| G0 计划与工程 | S00–S02 回执、版本锁、类型生成与小程序构建结果 | 修工程；不要开始业务堆代码 |
| G1 真实媒体 | S03/S04＋H03/H04：中文 MP4、ffprobe、两系统手机播放/保存/第二微信打开；关闭域名豁免 | 后端纯任务可继续；前端后续接线不得宣称已真机通过 |
| G2 数据与权限 | S07–S22：迁移约束、50 并发抽取、旧租约/撤回/改名竞态、CSRF、越权 | 不导入真实用户或开放真实活动 |
| G3 完整体验 | S23–S35＋H06/H07：后台发活动→用户生成→改名→分享→删除，全链路证据 | 修确切失败场景，不能用演示视频替代 |
| G4 可提审候选 | S36–S41＋H01–H08及H09所需材料：恢复演练、成本容量、同一 prod 构建、材料与权限证据 | 不提审、不发布；缺项保持 BLOCKED |
| G5 已上线 | S42/S43＋H10：平台发布状态、普通用户流程、监控/清理/备份证据 | 只能说审核通过或已上传，不能说可交付上线 |

C 不在场时可以准备资料和修卡片，门槛留为待审；不必等待 C 才编写所有独立模块。G0–G5 是本项目质量门槛，不冒充微信审核。

## 7. 审查时要问的五件事

1. 输入输出是否与本次 OpenAPI、当前 SQL 和命名一致，有无偷偷复用附件状态/路径？
2. 谁拥有资源；在并发、401、响应丢失、撤回、删除之后是否仍成立？
3. 测试有没有失败路径和实际业务断言，而非只有服务启动/页面截图？
4. 证据是否来自当前 SHA、真实命令和要求的设备，是否混入 mock/开发调试？
5. 下一卡所需产物是否真正存在；没有实现的命令是否被误写为 PASS？

## 8. 时间和成本的使用方法

每张卡是一次工作单元，目标可在一轮实现加一轮修复内审查，不承诺模型耗时。超过约 8 个实现文件或 500 行有效改动且涉及两个独立行为时，由 C/G 拆卡并更新依赖；新增锁文件和生成类型不计该参考阈值。先做 G1，再根据实测媒体耗时估服务器预算。备案/认证/审核是人工依赖，按实际结果排期，不用固定“6 周上线”保证。
